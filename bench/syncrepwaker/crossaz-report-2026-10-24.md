# SyncRep wakeup comparisons, 2026-10-24 UTC

Completed **144 accepted runs / 45,215,974 measured transactions**. The independent raw-log audit passed for all 64,966,395 full-run transactions. Six CPU-interrupted attempts containing 35 measured rows are excluded in full. The servers used by these benchmarks are stopped on both VMs; temporary RAM clusters are removed.

The wake-after-unlock patch has a clear gain in the CPU-focused RAM microbenchmark, including with the waker disabled. It does not establish a universal improvement on persistent storage or across AZs. The persistent 32 KiB and single-client tests have wide run-to-run throughput ranges; several tail improvements also have wide ranges. Treat small differences there as observations on these shared VMs, not significance tests.

All variants use the same parent pgbench executable and the same parent standby. These hybrid scores explicitly select limit 8; the enabled-worker default (on, limit 0) is not scored here. Before every run, the harness checked the effective waker settings and actual synchronous streaming/TLS connection.

Each case has three accepted runs per variant, a 5-second warmup and a 20-second measurement window. All disk cases use 128 clients except the single-client INSERT. The simple-update case uses pgbench `-b simple-update`, scale 10. Batch cases insert 10 or 1,000 empty payload rows per transaction. The 32 KiB payload is generated by SQL and stored with `STORAGE EXTERNAL`; TLS carries the resulting WAL, rather than a large client bind parameter.

`synchronous_commit=on` waits for one synchronous standby to flush WAL; `fsync` and full-page writes remain enabled. Shared buffers are 256 MiB, WAL buffers 64 MiB, max WAL size 16 GiB, checkpoint timeout 30 minutes and autovacuum off. Stopped primary and standby snapshots are restored and copied files fsynced before every run. pgbench history starts empty after restoration. tmpfs is a separate CPU control and does not model persistent-storage durability.

Run order rotates across rounds, with matching seeds 1000, 1001 and 1002. The later round-based runner saves a complete four-variant round independently, rejecting the entire round when a CPU guard triggers. It retries that round with the same seed/order after ten seconds with host busy CPU at most 3%. During measurement the primary/combined-host unattributed-busy guard is 10%; the shared remote standby has a separately declared 60% guard. Actual per-run values remain in the JSON. These guards do not detect every storage, network, hypervisor or scheduler disturbance. No unrelated workloads were stopped.

## RAM saturation and equal offered load

At saturation, the candidate hybrid8 median is 81,083 TPS versus 61,675 for base (+31.5%). Its p50 is 1.457 versus 0.842 ms (+73.0%), and p99 2.839 versus 10.722 ms (−73.5%). The candidate with the worker disabled reaches 81,161 TPS and p99 2.519 ms. The throughput gain therefore also exists without the auxiliary waker process.

The 50,000 TPS offered rate was chosen once after observing about 61,700 TPS baseline saturation, before inspecting fixed-rate results. All variants deliver approximately that same rate. Compare the response and execution quantiles below; tiny TPS differences at fixed offered load are not capacity gains.
