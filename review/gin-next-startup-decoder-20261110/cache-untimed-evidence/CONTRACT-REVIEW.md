The current generic GIN support API does not justify memoizing arbitrary callbacks. `ginvalidate.c` validates signatures and procedure numbers but does not require immutable support functions. `gin.sgml` permits opclasses to return arbitrary `extra_data` pointers. A catalogue IMMUTABLE label alone would not prove that callback-owned pointed-to state remains unchanged. The ternary shim also mutates and restores its input while collecting boolean recheck state. No generic result cache is implemented here.

A possible narrow alternative is a single last-vector memo for the exact builtin `gin_tsquery_triconsistent` OID and native function pointer, attached to one `GinScanKey`, not to shared `FmgrInfo`. `tsginidx.c` reads the query, check vector and extraction map and returns a ternary value; it does not mutate `extra_data` or use `fn_extra`. The builtin extraction function allocates its query map once per extraction. Such a prototype must restrict both extractor and callback to the reviewed builtin functions, keep query/strategy/collation/categories/extra-data lifetime fixed within the scan key, and leave arbitrary opclasses and the shims on their original path. A returned GIN_MAYBE must remain GIN_MAYBE. Direct native tri calls do not change `recheckCurItem`, so caching them must not overwrite it.

First step: `vector-probe.c` forwards every call to the actual builtin and counts consecutive equal check vectors of length at most eight separately for boolean and ternary callbacks. It compares context identity (query datum, extraction-map pointer, strategy, collation and length) before comparing the vector, and resets between static queries. This is untimed instrumentation; no results are cached. The deliberately VOLATILE declarations describe its counters honestly and demonstrate why signature validation alone is insufficient for generic caching. Callback share must come from a separate uninstrumented profile, not from this counter overhead.
