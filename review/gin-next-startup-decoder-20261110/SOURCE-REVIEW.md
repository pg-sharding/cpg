These are two independent alternatives over fixed B (`8a8c475037bfde101da23cc9b0364c9c020eca93`), with the same supplied prerequisite in every build. They are not a patch series. C9 is the existing lazy/gallop/exact-count comparison, not a new implementation here. Source-only canonical identities use `root <localhost>`; `SOURCE-IDENTITY-CORRECTION-r1.json` maps the original frozen build commits to byte-identical canonical trees.

S1 performs an exact entry-existence preflight before the main index startup. It applies only to multiple normal/default entries, with no partial match and fuzzy search disabled. A missing/empty inline entry becomes GIN_FALSE; other entries stay GIN_MAYBE. The existing ternary semantics must refute an entire scan key before the main startup is skipped. An existing posting tree is conservatively treated as present; no attempt is made to prove that tree empty.

The preflight uses the native entry-tree lookup under its ordinary locks. Its predicate-lock targets match `startScanEntry`: posting root for a found posting tree, entry leaf for inline and absent entries. It releases entry locks and pins without opening posting trees. Ordinary positive startup still computes the original frequencies, required/additional entry partition and fuzzy behavior. The temporary context, entryRes and recheck fields are restored to their initial state. The existing final scan cleanup still runs.

Rejected shortcut: setting `key->isFinished` in advance is not sufficient. `scanGetItem` calls `keyGetItem` before it tests completion, and `keyGetItem` asserts that the key is not already finished. S1 instead returns a boolean from startup and uses the existing final cleanup path. A second rejected shortcut is treating an arbitrary absent query entry as a conjunction: opclasses may implement OR/NOT or other logic, so only the original ternary callback can prove emptiness.

S1 adds an entry lookup pass for successful scans and nested missing-entry mapping work. OR, dense AND, positive skew, short inline lists, single-key, phrase, NOT, prefix, null/empty and off-path Seq controls are required. No improvement is inferred from the source change alone.

D1 adds a fixed batch of four complete one-byte deltas to the production all-segment decoder. It checks four available input bytes, four available output slots and all four continuation bits before the batch. Long integers, short tails, first-item handling, segment stepping and allocation growth keep their existing paths. The original per-integer varbyte decoder is already unrolled to seven bytes; D1 is a different experiment in batching four complete small integers. It does not change the on-disk representation or exported API.

Output allocation is deliberately unchanged. Upstream [CF7352](https://commitfest.postgresql.org/patch/7352/) already includes an output-size change in attachment 0005. The bounded read-only archive evidence is `PRIOR-ART-ALLOCATION-r1.json`, attachment 157871 / message 1155925, decoded SHA256 `56f8235f38f2702b4b57bae0607ca6a79643ae7f623a446043e3d76bc0567f5a`. That attachment was read as inert data only. D1 does not claim this allocation idea as new.

Qualification calls the actual installed compressor and decoder with independently generated valid ordered TIDs. It includes short runs/tails, larger dense lists, many segments, a first singleton followed by growth and 2–7-byte deltas. The separate native timing function includes decoder allocation, materialization and pfree; fixture compression and complete oracle verification are outside that boundary. It is not invoked by the correctness stage.

The old B/P10/P11 absent profiles and P11 regressions are prior measurements, not measurements of S1/D1. C9's full-read, OR and dense uninstrumented profiles are still required before claiming any decoder opportunity on C9. Profile percentages are diagnostic samples, not a causal latency decomposition.
