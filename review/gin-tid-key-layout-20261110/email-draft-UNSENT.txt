Hi,

I tested loading the four-byte GIN BlockId with memcpy, followed by a halfword reorder on little-endian hosts, instead of separate halfword loads. The attached P11 diff retains the original unsigned comparison key expression, block <<32 | offset. It does not change six-byte TID storage or assume four-byte alignment.

This follows an experiment using the compact block <<16 key, P10. Restoring the old key values does not remove the absent-query cost. The proposed load change therefore remains experimental, despite useful selective-query wins.

The new matched screen uses fixed B72, not current master. Below, percentages are medians of direct same-round backend-CPU changes, cohort0 / cohort1, with all observations retained:

The actual index_rescan/index_getbitmap/tbm_free adapter also retains the absent cost: P11/B +5.79 / +5.95% internal process CPU for5,000 scans, with B medians 56.159826 / 55.615619 ms and P11 58.981171 / 58.677464 ms per loop. These are native loop times, not SQL latency. Its selective loop improves -23.08 / -23.05%. Native and SQL boundaries, all negatives and exact B/T twins remain separate, without trimming,pooling or normalization.

P10/P11 have identical linked symbol addresses/sizes. Their .text sections differ only in54 SHL immediates16->32. Separate absent profiles are dominated by ginPostingListDecodeAllSegments in all three variants. Neither observation explains the runtime difference; no instruction-trace, hardware-cycle or causal claim is made. No full25-query or CREATE INDEX timing was promoted.

Setup: B72 72b9498df9a369e747f8d96efb5a6cd33c2451e2 plus the same supplied prerequisite; GCC13.3 -O2 -g -fno-lto, four clean matched builds, release timings, warm-cache200,000-doc FTS/JSONB/array fixture, JIT/parallel/memoize/autovacuum off,512MB shared_buffers. All four builds passed the original239 core tests and test_ginpostinglist, including assertions. Ordered Seq/GIN multisets, scalar answers, expected paths, prepared/cached rescans and native answers matched. Both P11 and its combined C11 counterpart passed1,009,216 actual-header ordering/exact-key properties; C11 has only production-unit/property coverage, no full C11 timing. Non-GIN release backend objects matched baseline byte-for-byte. Only x86-64 little-endian execution was tested.

Previous discussion: integer TID comparisons and private compressed-segment copying with deferred decoding were explicitly proposed in2014 [1]. This directly precedes the earlier lazy/adaptive C9 experiment. The current contribution is a bounded load/code-generation experiment and its measured tradeoffs, not a new algorithm or priority claim. The2015 uint64/32-bit compiler discussion [2] is portability context, not a reproduced issue here. The earlier R1 screen and complete negative data are linked in [3].
