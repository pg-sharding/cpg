# GIN: результаты K4 и D3, 11 ноября 2026

Сравнение выполнено на VM158, Linux x86-64, GCC 13.3, исторический
baseline B72 `72b9498df9a369e747f8d96efb5a6cd33c2451e2` с одинаковой
обязательной предпосылкой fixedB. Это не измерения текущего master.
Патчи K4 и D3 — независимые эксперименты, вместе они не измерялись.

В таблицах показано изменение времени: минус означает быстрее. Два числа
соответствуют двум размещениям процессов на одной VM. Проценты — медианы
отношений парных замеров, а не отношения приведённых абсолютных медиан.
Данные прогреты; физические чтения/записи в удержанных D3 замерах равны нулю.

## K4: компактная структура ключа поверх K3

Перестановка одного поля уменьшила `GinScanKeyData`: B — 152 байта,
контроль C без memo — 144, K3 — 160, K4 — 152. Это подтверждено проверками
установленных заголовков. Само уменьшение структуры не доказывает ускорение.

| Сценарий | K4 относительно B | Что это означает |
|---|---:|---|
| OR, полный SQL из пяти проб | −4,744% / −5,122% | Основная часть выигрыша уже есть в K3: −4,598% / −4,698%. |
| Тот же OR, K4 относительно K3 | −0,456% / −0,238% | Дополнительный вклад перестановки мал. |
| Dense AND, полный SQL | +0,090% / −1,247% | Исправление прежнего dense overhead не установлено. |
| `skew1000`, K4 относительно K3 | +0,178% / −0,134% | Устойчивого дополнительного выигрыша нет. |
| Отсутствующий ключ, AM, контроль C относительно B | +5,234% / +5,112% | Перестановка без memo тоже способна ухудшить время. |

Абсолютные медианы полного OR SQL: B 151,7905 → K4 144,5640 мс и
B 151,6425 → K4 144,9805 мс. Это пять проб в одном SQL, не время одной пробы.

Первый полный запуск сохранён как диагностический из-за посторонней нагрузки
в конце. Решение повторить весь неизменённый протокол принято до чтения
его итоговых времён. Второй запуск прошёл в более спокойном наблюдаемом
окне, но идентичные B/T бинарники в отдельных AM-сценариях всё ещё
различаются примерно на 6%. Результаты запусков не объединялись; строки
не отбрасывались и на контроль не нормировались. Рекомендовать перестановку
как общее ускорение пока нельзя.

Оба полных запуска: по 2880 сырых / 2400 удержанных наблюдений, 17 SQL и
семь AM-сценариев. Проверены пять чистых сборок, по 239 основных тестов
на сборку и отдельные проверки SQL, callback/budget и generic fallback. Независимые пересчёты
и повторное построение таблиц из опубликованного пакета прошли.

## D3: выбор режима декодирования сегмента

D3 выбирает пакетный цикл, если сегмент начинается с четырёх однобайтных
дельт; иначе использует скалярный цикл до конца сегмента. Явное inline
декодера убрало обнаруженные при компиляции вызовы на каждый элемент.
Размер основной функции вырос: B 589, D2 844, D3 1241 байт. Из этого
не выводится причина наблюдаемых времен.

| Сценарий | D2 относительно B | D3 относительно B |
|---|---:|---:|
| 128 плотных элементов, native CPU | −10,673% / −10,814% | −10,446% / −10,652% |
| Трёхбайтные дельты | +7,153% / +7,291% | −0,201% / +0,120% |
| Четырёхбайтные дельты | +6,203% / +6,306% | +0,319% / +0,047% |
| Двухбайтные дельты | +4,361% / +4,518% | +2,303% / +3,222% |
| Чередование коротких и длинных дельт | +16,408% / +16,746% | +1,559% / +1,445% |
| Длинная первая дельта, затем плотный участок | −10,461% / −10,904% | +0,204% / −0,042% |
| `skew1000`, полный SQL из 100 проб | −2,427% / −2,186% | −2,045% / −1,469% |

Для `skew1000` абсолютные медианы SQL: B 77,8575 → D3 76,2910 мс и
B 77,6110 → D3 76,4315 мс. D2 здесь остаётся немного быстрее D3.
Native метрика включает выделение памяти, декодирование/материализацию
и освобождение результата; это не время одной операции декодирования.

Регрессии D3 ещё остались. Одноэлементные сегменты дают +2,378% / +2,506%
к B. На длинной первой дельте с плотным продолжением D3 теряет выигрыш D2:
+12,108% / +12,080% к D2. На сценарии с первым одноэлементным сегментом и
последующим ростом результата D3 медленнее D2 на 8,390% / 8,712%.
Другие SQL-сценарии дают смешанные результаты; они сохранены полностью.
D3 — измеренный компромисс, а не замена без регрессий.

Четыре чистых сборки прошли по 239 основных тестов и posting-list checks.
Обычная квалификация: 188 SQL/prepared сравнений, 48 lifecycle сравнений,
84 native случая и 768 корректных смешанных входов. После отдельного smoke
выполнены семь SQL и 21 native сценарий: 3136 сырых / 2688 удержанных /
448 прогревочных наблюдений. Независимый пересчёт проверил 87360 числовых
полей, планы, настройки и ответы. Все 17 использованных жизненных циклов
тестовых серверов завершены; исходники, установки и модули не изменились.

## Следующая проверяемая гипотеза

Отдельный D4 draft исследует возврат к пакетной обработке внутри сегмента
после длинных дельт. Ограничение D3 известно из кода; выигрыш следующего
варианта заранее не предполагается. В частности, возможен возврат overhead
на чередующихся коротких/длинных дельтах. Сначала нужны проверка обычного
машинного кода и корректных входов, затем полный неизменённый набор micro
и SQL со всеми контролями. Этот draft не входит в измеренные результаты
D3 или K4.

Черновики писем не отправлены. Git/S3 подтверждения доставки хранятся отдельно от неизменяемых пакетов.
