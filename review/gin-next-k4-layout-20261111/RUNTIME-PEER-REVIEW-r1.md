# K4 runtime adapter: independent local review

Reviewed 2026-11-11. **PASS for the prospective runtime adaptation; no blocking runtime error found.** This is source/protocol review, not an actual qualification, smoke or timing PASS. Root owns the already-running VM158 build chain and later live gates. No frozen file or remote process was changed by this review.

All entries in BUILD-INPUTS-K4-r1.json and RUNTIME-INPUTS-K4-r1.json were rehashed locally. Qualification native-oracle.c, budget-oracle.c, vector-probe.c and Session, plus timing Session/common/validate/gin-am-micro.c, are byte-identical to the proven K3 inputs. All old 23 timed cases are unchanged; the 24th is the already-existing separate_keys SQL case, not a newly invented fixture. The current C canonical commit, K3 and K4 pins resolve through the source plan; T maps to B.

The five source builds are B,C,K3,K4,K4_assert; timed roles are B,T,C,K3,K4. Installed modules using the private GinScanKeyData ABI compile against each variant's own 907 headers. The AM timing module uses public access-method APIs and no private scan-key fields; its common B-header build is therefore compatible with the layout variants. Build-time installed ABI assertions remain the proof of actual key sizes 144/152/160, not Python-model assumptions.

Qualification maps C to B's no-cache expectations, K4 to K3 and K4_assert to K3_assert. Cache-present macros are false only for B/C; budget 64 applies to all K variants. Both expected_fields and compile_macros exactly match the mapped old protocol. Independent sums agree: 55 budget cases, 64680 calls, 660 initializations, 110 context resets, 270 dispatch transitions. The native oracle covers valid ternary vectors, recheck sentinels, entry counts 8/9 and hidden entries. The budget oracle covers consecutive 63/64/65, hit reset, interleaved cumulative misses, key independence and context reset. The generic fallback retains the distinct volatile support-function OID/address checks. These are qualification calls, not timing samples.

The odd-size Williams schedule is correct: 5 forward cyclic orders plus their reversals. In 10 retained rounds every role occupies each position twice and every directed adjacent pair occurs twice. Two preceding warm rounds are excluded from statistics. Per cohort: 24 × 5 × 12 = 1440 raw, 1200 retained, 240 warm; across two cohorts 2880 / 2400 / 480. There are 17 SQL cases with 3 metrics and 7 AM cases with 4 metrics: 79 metrics per role, 395 absolute groups and 790 paired groups per cohort, 7900 direct round pairs. All 10 role pairs remain available. Cohort 1 reverses case and physical placement order; cohorts are kept separate.

Port ranges are disjoint: core 47100..47104, posting 47130..47134, qualification 47160..47165, smoke 47200..47204, cohort 0/1 timing 47210..47219. Short socket directories lie under the namespace's s/ and differ across qualification/smoke/cohorts. The longest prospective socket path is 71 bytes, below the helper's 104-byte bound. Fifteen copies are created/fsynced before assignment: 5 smoke-only and 10 untouched accepted copies for two cohorts. The selected copy indices, reversed role mapping, prefix mapping and fresh socket names consistently use 5 rather than the old 4.

Timing boundaries remain explicit: backend schedstat CPU and monotonic client wall cover a whole command; SQL Execution Time covers the whole EXPLAIN command's SQL execution; AM inner CPU/wall cover the actual index_rescan/index_getbitmap/tbm allocation/free loop. The native AM work unit excludes executor/heap visibility and is not ordinary SQL latency. Literal queries are separate extra warming commands before every measured command. The new literal monotonic timestamp allows analyzer and offline review to establish literal timestamp ≤ measured monotonic start, without the D2 cross-clock limitation. All input/protocol/seed/build/qualification bindings are checked at stage boundaries. The run stage separately requires the external smoke review receipt and cannot follow prepare/smoke automatically.

Two reporting limits require attention when actual data arrive:

- The runner/validator verifies literal answers and index/loops/root rows, but does not preserve and compare a complete semantic plan signature as the later D2 runner did. The full JSON plans are retained in raw, so root's actual smoke/final review can compare shape, actual rows/loops and rechecks separately. Expected settings also need explicit root review; the runtime records equal settings across roles, and audit-results checks jit/memoize/parallel, not every expected flag.
- The new audit-results.py imports protocol and validate. It independently reconstructs row ordering and values/medians, but currently does **not** independently reconstruct every spread, mean/stdev/MAD, differences, direct arrays and exact group completeness. Its current successful status must be described as a count/identity/value/median audit, not a full independent numerical recount. It is not a blocker to qualified runtime execution, and it is not part of the already-imported remote inputs. Stronger final arithmetic review can remain a separate local step without changing the frozen runtime.

No new benchmark result is claimed. In particular, the design can compare C/B (layout without memo), K4/K3 (layout with memo), K3/B and K4/C (memo under two layouts), but neither the size reduction nor these comparisons alone establish the cause of earlier dense overhead. Code layout, field displacement, allocator placement and exact-twin variation remain possible contributors requiring evidence.
