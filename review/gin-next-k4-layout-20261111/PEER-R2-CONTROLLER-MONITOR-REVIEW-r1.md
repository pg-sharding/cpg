# R2 controller and host monitor: local peer review

Reviewed 2026-11-11, before the accepted r2 repeat. No script was executed on the VM and no root-owned or frozen file was edited by this peer review. **Final source review PASS:** root addressed the SIGTERM/SIGINT cleanup findings in the new wrapper, and all frozen inputs remain unchanged. The final reviewed hashes and bounded scope are recorded in [PEER-R2-CONTROLLER-MONITOR-FINAL-r1.json](PEER-R2-CONTROLLER-MONITOR-FINAL-r1.json). Actual live shutdown proofs and monitoring review remain required.

The wrapper uses a nonexistent R/r2 parent and R/r2/timing-r2 output. The frozen campaign therefore creates sockets under fresh R/r2/s, independently of R/s. It does not remove or reuse r1 directories. First port 47300 gives smoke ports 47300..47304 and accepted cohort ports 47310..47319, disjoint from r1 and the earlier build/qualification ports. The three campaign stages call the unchanged frozen inputs and source/build/qualification bindings with fixed CPU pairs 0:4,4:0. The screen remains 24 cases, five roles, two cohorts, two warm rounds plus ten retained rounds: 2880 raw / 2400 retained / 480 warm. Prepare/smoke remains separate from the externally reviewed run gate.

The wrapper preserves attempts in new state/log paths, checks every build/runtime manifest entry, applies nice 10 and a 3 GB address-space limit, bounds a child wait at 3600 seconds and records command/monitor digests. Its load-average preflight is prospective rather than an outcome-based timing filter. Completion of unrelated build/qualification work and absence of foreign CPU work still depend on root's actual preflight review; the one-minute load average alone cannot prove them.

The original interruption issue was specific: the wrapper sent SIGTERM to a campaign with no SIGTERM handler, so Python's default termination could skip its finally cleanup. Root changed the guarded child-wait cancellation/timeout path to SIGINT and explicitly installed signal.default_int_handler for SIGINT in the new wrapper before Popen. The latter matters because shell-background launch can inherit ignored SIGINT; start_new_session=True alone does not reset it. A local two-child Python experiment confirmed that inheritance and the explicit-handler reset, without running any backend or VM process. Wrapper SIGTERM itself raises KeyboardInterrupt. The unchanged campaign can consequently enter its finally cleanup on this interruption path. The cleanup wait remains bounded and failures preserved. This is source review, not an actual cancellation experiment or a guarantee of cleanup under every failure; final owned-process/socket proofs remain mandatory.

The monitor reads only /proc/<pid>/stat names, starttime and user/system CPU counters; it never reads command-line arguments or signals the observed processes. Field positions are correct after removing the parenthesized comm: state is index 0, utime/stime are indices 11/12 and starttime is index 19. The (PID,starttime) key prevents PID-reuse attribution. Its CPU value is per-process aggregate one-core percentage, so multithreaded work can exceed 100%.

Monitoring is bounded at five-second intervals for at most 3600 seconds, with only the top 20 positive CPU consumers saved per interval. It pins itself to CPU 6 at nice 19. The recorded host topology places CPU 6 on physical core 3, separate from server/client CPUs 0/core 0 and 4/core 2; this should remain true in the actual r2 topology receipt. Its own /proc reads and JSON writes still create some host activity and can share VM/cache/memory resources.

This observation cannot prove an interference-free run. It misses a process that starts and exits between snapshots, and misses a process's CPU before its first observed endpoint or after its last observed endpoint. Only the top 20 deltas are retained. It records no per-thread CPU residency, affinity history, throttling/steal time or exact alignment of another task with each SQL command. Five-second sampled realtime timestamps give coarse overlap evidence. Also, the wrapper does not currently wait for a monitor-ready acknowledgement before launching the campaign, so monitoring of the earliest startup interval is not guaranteed. An empty consumer list is not proof that no foreign work occurred. Review the actual monitor record, status and host context alongside r2 outcomes; do not use it to trim individual samples or normalize timings.

The monitor's terminal receipt must show that the selected run status was observed. A timeout, failed monitor or BOUNDED_OBSERVATION_ENDED cannot be described as a complete monitoring record, even when the campaign itself passed. The wrapper currently checks this separately after the campaign. Its cleanup signals target only its own monitor/campaign children, never the foreign workload.
