Subject: [RFC PATCH] Load GIN BlockId words together for TID comparisons
Status: UNSENT EXPERIMENTAL DRAFT; repeated regression remains

Hi,

I tested a small code-generation change to ginCompareItemPointers: load the four-byte BlockId with memcpy, reorder its halfwords on little-endian hosts, then construct the unsigned comparison key. It retains six-byte TID storage and two-byte alignment, with no eight-byte overread. The prototype also changes the transient block shift from32 to16; a separate follow-up restores the original layout to isolate this difference. That is a hypothesis, not a diagnosis.

P10 applies to the fixed B72 baseline. C10 is the same change on the previously tested combined lazy/adaptive C9 prototype. They are alternative patches, not a series. Current master was not measured.

SQL absent B/P10 medians are 1.594819 / 2.378144 / 1.696371 / 2.441244 ms. Full min/median/max, SD/MAD and every metric/pair are included in the results packet.

The P10 absent cost also repeats in the real index_rescan/index_getbitmap/tbm_free adapter: +5.05 / +3.94% internal process CPU for5,000 scans. It is not explained away using the exact B/T executable twin. C10 has smaller native benefits but retains positive off-path Seq CPU medians. This version is not ready to propose as a general improvement; no full25-query timing or CREATE INDEX result is claimed. All negative cases and twins remain visible.

Setup: B72 72b9498df9a369e747f8d96efb5a6cd33c2451e2 plus the same supplied prerequisite, GCC13.3 -O2 -g -fno-lto, five clean matched builds, release timings, JIT/parallel/memoize/autovacuum off,512MB shared_buffers, warm-cache200,000-doc synthetic fixture. Six roles B/T/P10/C9/U/C10,13 SQL plus seven actual-AM cases, two warm and12 retained balanced rounds, two reversed CPU/slot/session/case-order cohorts:3,360 raw observations. B/T and C9/U use exact executable twins; no trimming, pooling or normalization.

All five builds passed the original239 core tests and test_ginpostinglist. Ordered Seq/GIN multisets, scalar answers, paths and prepared/cached rescans agreed, including assertions. Actual installed headers were used in the native adapter/property check; each new helper passed1,009,216 ordering cases including extreme TIDs and both alignments. Non-GIN backend objects matched B byte-for-byte. Only x86-64 little-endian execution was tested.

Previous discussion: Heikki already proposed integer TID comparisons and deferred consumption of copied compressed posting segments in2014 [1]. This directly precedes the lazy C9 idea. The present contribution is a small load/code-generation experiment and its measured tradeoffs, not a new algorithm. The existing comparator already used uint64 keys. Noah’s2015 inline uint64/AIX discussion [2] is portability context, not a reproduced failure here. The bounded archive search establishes no priority claim.
